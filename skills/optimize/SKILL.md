---
name: optimize
description: Use when the user asks to optimize, speed up, shrink or push a measured number toward a target, such as latency, throughput, memory, bundle size, cost or a score. Runs rounds of distinct hypotheses in parallel worktrees against one metric, keeps only what beats the baseline beyond noise, and stops at the target or after two dry rounds. Not for work without a number to move.
argument-hint: "<what to optimize> --metric <command> [--higher] [--target <n>] [--guard <command> <max>]... [--paths <globs>] [--rounds <n>] [--parallel <k>] [--out <file>] [--no-review]"
---

1. Lock the contract. `--metric` is a command whose last output line is one number; lower is better unless `--higher`. Each `--guard` is a second command whose last line is a number, with a maximum (absolute, or `+N%` of its baseline) it must not exceed while the metric moves: memory, bundle size, a p99, a score that must hold. `--paths` are the files a hypothesis may change; absent, the module the request names. `--rounds` defaults to 6; `--parallel` is the number of hypotheses per round, and so of workers and worktrees running at once, default 3. No metric command, or one whose last line is not a number: ask for it through the host's question tool, contract in `<plugin root>/skills/scope/references/asking.md` (`<plugin root>` is the parent of the `skills/` directory this file lives in), and stop there; owned paths named by neither `--paths` nor the request are asked for the same way, recommending the files the metric command exercises.

2. Baseline. The owned paths must be committed, since every hypothesis starts from a worktree of a commit: an uncommitted change there prints `blocked: commit or stash <paths> first` and stops. An existing `optimize/<slug>` branch is a stopped run's champion: print `blocked: optimize/<slug> exists from a stopped run; land it (git diff HEAD...optimize/<slug> | git apply) or delete it first` and stop. Measure in a detached worktree of `HEAD` (`git worktree add --detach`, plus the install step when the metric needs built dependencies), never in the main tree; it is the champion tree until a round keeps something. A metric that fails there names what a fresh checkout lacks (ignored data, an env file, a build step), and step 4 gives the same to every worktree. A metric whose number comes from a process started elsewhere (a dev server, a seeded database, a browser session) succeeds there while measuring the main tree whatever the worktree holds: read the command for that case, and when it does not start the process from the checkout it runs in, ask for a command that does through the host's question tool as in step 1, and stop there. Run the metric three times there, and each guard once; the baseline is the median and the noise band is the spread, never below the smallest unit the metric prints. When the band exceeds a fifth of the distance to the target (of the baseline itself without a target), raise the runs to five, then seven, and record the count; a band still wider than that is reported as `noise: metric too coarse for the target` and the loop runs on medians anyway. That count is the run count everywhere below. `sh <plugin root>/scripts/checks.sh <owned path>` names the regression check; none configured means behavior is proven only by what the metric itself exercises, and the report says so. One metric run longer than about five minutes sets `--parallel` to 1; say why.

3. Hypotheses. Profile first when the stack has a profiler: one run of the metric under it in the champion tree, the top frames written to the ledger, and the families named from what dominates; without one, name them from reading the code and say so. Read the ledger, then name `--parallel` hypotheses from different families, one change each so the ledger can say which one moved the number. Time: algorithmic complexity, I/O and round trips, caching and memoization, batching and vectorization, allocation and copies, concurrency and laziness, build and dependency configuration. Size: dead code, duplication, dependencies, formats, compression. A score: the terms that dominate it. A discarded family returns only with a mechanism the ledger has not recorded, written down as such; the one exception is a candidate that beat its baseline beyond the band and held every guard but lost the keep, on files disjoint from the champion's: replayed on the champion as a single change, it is this round's first hypothesis. Nothing new to name: stop (step 7).

4. Fan out. For each hypothesis: `git worktree add --detach <dir> <base>`, where `<dir>` is under `mktemp -d` and `<base>` is the champion commit, `HEAD` before the first keep; run the project's install step there when the metric needs built dependencies, and provide whatever the baseline worktree showed a fresh checkout lacks. Give a `atlas-worker` (Codex: `atlas_worker`; Opus / `gpt-5.6-terra` when the hypothesis crosses several files) the contract: this hypothesis only, the owned paths inside its worktree, one metric run to confirm the code executes and what it printed, the regression check, `git diff --stat`. Workers never touch the main tree, and their numbers are not verdicts: parallel runs on one machine contend for it.

5. Measure, then verify. When the round's workers have all returned, run the metric the baseline's run count in each worktree whose regression check passed, and every guard once, one worktree at a time with nothing else running; from round two on, measure the champion tree again in the same pass and take its median as the round's baseline, so a drift in the machine does not read as progress. Discard a candidate whose median does not beat that baseline by more than the band, or that pushes a guard past its maximum; being faster and wrong, or faster and heavier than allowed, is a regression, and so is a change that narrows what the metric measures (a test skipped, a benchmark shortened, a sample reduced), whatever the number says. Rerun the regression check in the best one, and discard what does not hold.

6. Keep at most one per round. In the winning worktree: `git add -A -- <owned paths>`, `git commit -qm "optimize round <n>: <family>, <mechanism>"`, `git branch -f optimize/<slug> HEAD`; that commit is the champion and its worktree the champion tree. Remove the worktrees of discarded hypotheses and the replaced champion tree with `git worktree remove --force <dir>`. Record every hypothesis in the ledger: round, family, mechanism, the values, median, delta against the baseline it ran on, kept or discarded and why; then the run's KPIs as the block below prints them, so a run that stops early still reports them. Rewrite the ledger file after each round: `--out <file>`, else `docs/optimize-<yyyy-mm-dd>-<slug>.md`; say where it went.

7. Stop the loop when the target is met; or two consecutive rounds kept nothing while every hypothesis in them was a family or mechanism the ledger had not tried; or the round budget is spent; or step 3 found nothing new. Otherwise return to step 3.

8. Land the champion, when a round kept one: `git diff HEAD...optimize/<slug> | git apply` in the main tree (three dots: the diff from the merge base, so commits the main tree took during the run are not undone), then `git branch -D optimize/<slug>`; remove the champion tree either way. Run the metric its run count on the main tree, the guards and the regression check once, and print:

```
metric: <command> - lower | higher
kpi: baseline <median> (band <spread>) -> final <median>, delta <n> (<percent>), target <met | gap <n> | none>
kpi: rounds <n>/<budget>, hypotheses <n>, kept <n>, discarded <n> (<most common reason>), wall <minutes>
kpi: regression <command> - pass | fail (also fails on baseline) | fail (new) | none configured
kpi: guard <command> <baseline> -> <final> (max <n>) - held | broken
profile: <top frames, or none available>
round <n>: <family> / <mechanism> - <median> - kept | discarded: <why>
stopped: target met | two dry rounds | budget spent | no new hypothesis
ledger: <path>
```

Then invoke `review` on the applied diff (Skill tool `atlas:review`, `$review` on Codex) unless `--no-review` was given or nothing was kept. When review changed a file, run the metric its run count and each guard once more on the main tree, print the `kpi: baseline` and `kpi: guard` lines again and carry them into the ledger; a repair that puts the metric back inside the band or a guard past its maximum is reported there, not hidden by the block above. Do not commit here; ship makes the real commit from the applied diff when asked.

Stop when the block is printed, review has run or was declined, and any review edit was re-measured. Never widen the owned paths to reach the target: a target the owned paths cannot reach is reported, not chased.
